# Количественная оценка качества ПС «TechnoSoft Bonus» (ЛР 11)

Модель — иерархическая модель качества методички (рисунок 56): 6 характеристик и их подхарактеристики. В перечне
методички подхарактеристик **28** (6 + 4 + 5 + 3 + 5 + 5), оценены все. Для каждой метрики X = A/B или X = 1 − A/B,
где A — измеренное значение, B — базовое; X округлено до двух знаков.

Все измерения выполнены 25.11.2026 на **установленном дистрибутиве** (`release/dist/TechnoSoftBonus-1.0.zip`,
установка по `README.txt`, см. `install-check.md`): macOS 26.5.2, Java 21, PostgreSQL 14.18, Google Chrome; клиент
раздаётся сервером на порту 8080, БД — установочная `technosoft_bonus` (второй экземпляр на порту 8081 — БД
`technosoft_bonus_replay`, восстановленная из той же резервной копии). Клиентская программа измерений и сервер работали
на одном компьютере. Скрипты и сырые данные — `release/metrics/` (сценарий полного прогона `run-all.sh`,
результаты `release/metrics/out/*.json`); статический анализ — по исходному коду проекта; мутационная проверка — в копии
серверной части.

## Найденный дефект D-2 и что сделано

При первом измерении PERF-3 (20 одновременных массовых начислений, пул соединений 10 — значение по умолчанию)
сервер перестал отвечать: массовые начисления завершились ответом 500 или не дождались ответа за 60 с, запросы
сотрудника в это время — 500 через 30 с (`out/mass-accrual-c20-pool10.json`, дамп потоков `out/mass-accrual-jstack.txt`).
Причина (по дампу потоков): каждый запрос начисления держит соединение с БД, а после фиксации транзакции обработчик
`NotificationListener.onOperationRegistered` (`@TransactionalEventListener(AFTER_COMMIT)` +
`@Transactional(REQUIRES_NEW)`) запрашивает второе соединение. Когда одновременных запросов не меньше размера пула,
все соединения заняты потоками, ждущими второго соединения, — ожидание длится до тайм-аута пула (30 с) на каждое
уведомление. Опасное следствие: операции при этом уже зафиксированы (250 операций), а клиент получает ошибку —
повторная отправка создаст дубли.

Код слушателя (`service/listener`) по условиям пакета не менялся. В дистрибутиве ограничение снято настройкой
(`config/application.yml`): потоков обработки запросов 40 (`BONUS_HTTP_THREADS`), пул соединений 45
(`BONUS_DB_POOL_SIZE`) — пул больше, чем потоков, которые могут одновременно держать соединение (40 + 1 поток
планировщика), поэтому взаимная блокировка невозможна. После настройки: 20 одновременных массовых начислений — 500
операций за 0,27 с, отказов нет; в пробном прогоне с теми же значениями (заданными переменными окружения) 100 одновременных массовых начислений — 2 500 операций за 1,2 с, запросы сотрудника p95 66 мс. Исправление в коде (для разработчика):
записывать уведомление в той же транзакции (как `AuditListener`, обычный `@EventListener`) или выполнять асинхронно
в отдельном ограниченном пуле.
